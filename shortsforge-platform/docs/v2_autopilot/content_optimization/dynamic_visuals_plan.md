# AutoPilot V3: Dynamic Scene-by-Scene Visuals

## The Monetization Problem
YouTube, Facebook, and Instagram monetization algorithms are strictly gating channels based on two factors:
1. **Audience Retention (Watch Time):** Modern audiences have short attention spans. If the visuals don't change every 5-10 seconds, they swipe away, killing your watch time and virality.
2. **"Reused Content" Penalties:** If you upload dozens of videos using the same `gameplay.mp4` background or a single static zooming image, YouTube's automated systems flag the channel as "Repetitive/Spam" and permanently deny monetization.

## The Solution (Algorithm Breaking)
We will upgrade the engine to artificially recreate the pacing of a human editor. The AI will break the story into tiny "Scenes", fetch a highly relevant, unique image for *every single scene*, and stitch them together. 

---

## Zero-Risk Architectural Blueprint (New Mode)
To ensure we do not break your currently stable, working system, we will build this as a **completely parallel new mode**. 
Your current pipeline will remain 100% untouched as the "classic" mode.

### Phase 1: Database & Config Update
**File:** `scripts/add_channel.py` & Database
- Add a new `visual_mode` toggle to the `channels` table (options: `classic` or `dynamic`).
- **Future-Proofing Config:** Even though we are only building Dynamic Images for now, we will add a configuration field (e.g., `dynamic_media_type = 'image'`) so that if we ever want to build Dynamic Videos in the future, the architecture is ready for it.

### Phase 2: Parallel Scene Generation
**File:** `scripts/story_maker/assembler.py`
- We will NOT touch the existing `build_part()` function. 
- Instead, we will create a brand new, isolated `build_dynamic_part()` function. 
- **Image-Only MVP:** To keep things perfectly simple and stable, this engine will ONLY support Dynamic Images for now. It will use DuckDuckGo to scrape images, and use FFmpeg to animate them with a slow zoom.
- It will break the `.srt` timings into scenes, fetch an image for each scene, and use FFmpeg `concat` to stitch them.

### The "Storage Nightmare" Solution (Temp Management)
If a video is 10 minutes long, changing images every 10 seconds means downloading 60 images. To ensure this doesn't become a hard drive nightmare:
1. **Isolated Folders:** All images for a specific video will be saved in a temporary folder: `data/video_temp/{topic}/part_{N}_assets/` (e.g., `scene_1.jpg`, `scene_2.jpg`).
2. **Auto-Cleanup:** The absolute millisecond that the final `master_video.mp4` is successfully generated by FFmpeg, the system will **permanently delete** the entire `part_{N}_assets/` folder. Zero bloated disk space.
3. **Scene Length:** We will make scenes roughly 10-15 seconds long (instead of 5 seconds) to drastically reduce the number of images we need to download and stitch.

### Phase 3: Pipeline Routing
**File:** `scripts/story_maker/run_pipeline.py`
- When the pipeline runs, it will simply check the database:
  - If `visual_mode == 'classic'`, it uses your current safe code.
  - If `visual_mode == 'dynamic'`, it routes to the new advanced engine.

### Phase 4: Master Concat Assembly
**File:** `scripts/story_maker/assembler.py`
- Once all `scene_X.mp4` files are generated in the temp folder, `assembler.py` will use the FFmpeg `concat` demuxer to flawlessly stitch them together into one seamless video.
- Finally, it will overlay the background music track across the entire master video using `amix`.
